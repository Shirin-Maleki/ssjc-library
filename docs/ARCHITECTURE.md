# Architecture

Status: Phase 0 — revised after first architecture review (2026-09-13). Nothing in this
document has been built. See the changelog at the end for exactly what changed in this
revision, and [`docs/DECISIONS.md`](DECISIONS.md) for the full reasoning behind each choice.

## 1. High-level shape

```
Google Drive (original cover photos, source of truth for images)
        │
        ▼
   Ingestion pipeline (single add + bulk import share this)
        │
        ▼
Postgres / Supabase  ◄────────────────────────►  Next.js application (staff + admin UI)
   (canonical data)                                        │
        │                                                   │
        ▼                                                   ▼
Google Sheets (generated, read-only            Object storage (display-optimized
 teacher projection — never canonical)          cover images, derived from Drive originals)
```

Postgres is the single source of truth for catalog data. Google Drive is the source of truth
for original cover images. Google Sheets is a **derived projection**, regenerated from
Postgres, never edited back into it. The Next.js application is the only interaction layer
for staff; a separate standalone script handles bulk import (§16 — this is a correction from
the first draft, not a restatement).

## 2. Frontend architecture

- **Framework:** Next.js (App Router), React, TypeScript, Tailwind CSS.
- **Rendering model:** Server Components for data-heavy, read-mostly views (search results,
  book detail, admin queues); Client Components only where interaction demands it (camera
  capture, voice input, autocomplete, filter panels, the Add-a-Book wizard).
- **Mutations:** Next.js Server Actions for all writes; Route Handlers (`app/api/*`) only
  where something needs a real HTTP endpoint (OAuth callback, a cron target for Sheets
  reconciliation).
- **Component primitives:** Radix UI primitives (unstyled, accessible) styled with Tailwind —
  full control over the visual direction while getting correct keyboard navigation, focus
  management, and ARIA semantics for dialogs/comboboxes/tabs for free.
- **State management:** no global state library — server state from server
  components/actions, local component state for ephemeral client-only interaction (wizard
  step, camera blob, voice transcript, unsubmitted filters).
- **Images:** `next/image`, sourced from the display-optimized copy, never directly from
  Drive (§5).
- **Fonts:** Poppins via `next/font/google`, weights 400/500/600/700 only.
- **Routing/access:** route groups separate public, staff, and admin areas;
  `middleware.ts` enforces session requirements before any protected route renders.

## 3. Backend / server architecture

No separate backend service for the web application — Next.js Server Actions + Route
Handlers, appropriate at this traffic scale. Bulk import is explicitly **not** part of this
layer — see §16.

**Data access, schema, and migrations: Drizzle**, not Kysely (revised this review — see
[`docs/DECISIONS.md`](DECISIONS.md) for the full Kysely-vs-Drizzle comparison). Drizzle is a
thin, SQL-transparent query builder like Kysely — not a heavyweight ORM like Prisma, so the
original "avoid ORM magic" reasoning still holds — but its schema is defined as plain
TypeScript (`src/lib/db/schema/*.ts`), which is the single source of truth for both runtime
types (no separate codegen step to remember) and generated migrations (`drizzle-kit
generate`). For this project specifically — a schema that will keep iterating through several
more review rounds, built primarily by AI coding agents editing files directly, maintained
long-term by a designer rather than a database specialist — reading and editing one
TypeScript schema file is a meaningfully lower-friction, lower-error loop than hand-writing
SQL migrations and separately regenerating types, without giving up SQL transparency (Drizzle
still produces plain, inspectable, hand-editable SQL migrations).

**Migrations:** generated by `drizzle-kit` into `drizzle/migrations/` — plain, numbered
`.sql` files, still fully portable to any Postgres host; Drizzle Kit is the single migration
tool (we do not also use the Supabase CLI's migration feature, to avoid two systems tracking
migration state against the same database). The Supabase CLI may still be used purely to run
a local Postgres+pgvector instance for development, independent of migrations.

## 4. Canonical database

**Postgres, hosted on Supabase.** Portability stance unchanged from the first draft: no
Supabase Auth, no Supabase-only RLS dependency, no Supabase Storage for canonical images —
schema and queries are standard SQL/Postgres, portable to Neon/RDS/self-hosted with a
connection-string change. pgvector is enabled for semantic search (§12).

## 5. Relational data model

Full schema in [`docs/DATA_MODEL.md`](DATA_MODEL.md) — revised this review. Summary of what
changed and why (full detail in the data model doc):

- **Books vs. copies, split.** The bibliographic/edition record (`books`) is now distinct
  from physical instances (`book_copies`). This was a real gap in the first draft — putting
  `home_location`/`current_location` directly on `books` could not actually represent "two
  copies of the same edition, one in the preschool library, one in Blue Room," which is
  explicitly a near-term need. A teacher adding another physical copy of an existing edition
  now inserts one `book_copies` row; "Copies: 2" is a derived count, never a stored/drifting
  number; copy IDs are never shown to teachers.
- **No separate Work entity.** Considered and rejected as real bibliographic overengineering
  for this collection (see `docs/DATA_MODEL.md` §2) — the lightweight, optional
  `work_groups` linking table from the first draft is the right level of sophistication, and
  since nothing in v1 uses it, it's deferred entirely rather than built unused (§12 below).
- **Provenance and confidence** are still unified in one table, now renamed
  `book_field_provenance` and redesigned to preserve a full evidence history (append +
  supersede, not overwrite-in-place) with a four-way source classification (external
  provider / AI-inferred / human-corrected / human-verified) — see `docs/DATA_MODEL.md` §6.
  The set of tracked fields (`field_key`) is deliberately **not** a database enum — it's
  validated against a centralized, extensible registry in application code
  (`lib/metadata/field-registry.ts`), so adding a new tracked metadata attribute is a code
  change, not a schema migration.
- **Language** is no longer a reference table — it's a plain validated text column backed by
  one shared application constant, removed on review as a table that existed for reference
  completeness rather than a real admin-management need (unlike `physical_categories`, which
  genuinely needs to be admin-editable data).
- **Contributors, tags, and physical categories** are unchanged from the first draft — see
  `docs/DATA_MODEL.md` for full column detail.

## 7. Original capture vs. display cover

**Sharpened this review** — these are explicitly two different things, never conflated:

- **Original capture** — the actual photograph taken of a physical book (or the original
  bulk-import file), archived to Google Drive, retained for provenance/review, **never**
  exposed directly to a browser.
- **Display cover** — whatever is efficient to actually render in the app. Not assumed to be
  the Drive file.

**v1 fallback order** (configurable via `system_settings`):

1. **A derived, resized copy of our own photographed original**, generated at ingestion time
   and stored in Supabase Storage — preferred *first*, not as a fallback, because it's a
   photo of the school's actual copy, which matters more for a "find it on the shelf" tool
   than a generic internet thumbnail of a possibly-different printing. This is the
   justification for using a second storage service at all: Drive isn't built for fast public
   hotlinking, and Supabase Storage is already part of the stack, not a new vendor.
2. **A metadata provider's cover thumbnail** (Google Books) — used only when our own derived
   image isn't available (a processing failure, or a pre-existing record).
3. **A server-side Drive proxy route**, streamed on demand — last resort only, since it's
   exposed to Drive API latency/rate limits; guarantees something always renders.

## 12. Search architecture: layered retrieval with graceful degradation

**Rewritten this review** to explicitly define discrete layers and guarantee the system stays
useful with zero AI/embeddings availability — semantic search augments, it never replaces,
conventional search.

```
Layer 1 — Exact / normalized matching
  Direct match on title, normalized author name, publisher, ISBN, category, language.
  Pure SQL. Zero AI dependency. Runs first; short-circuits obvious lookups.
        │
Layer 2 — Structured filters & tags
  Age-range overlap, fiction/nonfiction, format, visual attributes, tag matches — applied as
  SQL WHERE clauses from either the browse/filter UI directly, or from constraints an LLM
  extracted from natural language (see below). Pure SQL once constraints are known.
        │
Layer 3 — Postgres text/trigram search
  tsvector/tsquery full-text ranking + pg_trgm fuzzy/typo-tolerant matching over title,
  contributors, description, tags. Pure SQL. Zero AI dependency.
        │
Layer 4 — Semantic/vector retrieval (only when an embedding provider is configured/reachable)
  pgvector cosine similarity over the post-filter candidate set, for the vague/thematic/
  emotional remainder of a query that Layers 1–3 can't resolve.
        │
Layer 5 — Ranking & grounded explanation
  Composite score combining whichever of the above signals are actually available; a
  per-result explanation templated from the attributes that actually matched (never a
  free-form LLM explanation).
```

**Natural-language query interpretation** (turning "something gentle about separating from a
parent" into Layer 1/2 constraints plus a semantic remainder) uses an LLM call — but this,
too, degrades gracefully: if that call fails, times out, or no LLM provider is configured, the
raw query text is run directly through Layer 3 (full-text/trigram) as a plain keyword search
rather than failing outright.

**Composite ranking:**

```
score = w1·exact_match + w2·filter_fit + w3·text_rank + w4·semantic
        + w5·age_fit + w6·visual_match + w7·duration_fit
```

Weights are configurable via `system_settings`. When Layer 4 is unavailable, `w4` is treated
as zero and the remaining weights are used as-is (not artificially inflated to compensate) —
absence of a semantic signal simply means ranking relies on Layers 1–3, which is a fully
functional, fully deterministic search experience on its own; it is never a broken or
degraded-looking result set.

**Net effect:** Layers 1–3 require zero AI and zero external API — pure Postgres — matching
the brief's original requirement that teachers must not have to use AI at all (the
browse/filter path already guaranteed this; this revision extends the same guarantee to the
natural-language/voice search path).

Autocomplete remains a separate, simpler, indexed `ILIKE`/trigram query directly against real
column values, unaffected by this layering.

## 14. Staff / admin authentication & session architecture — full technical specification

The shared-password UX is unchanged; this section makes the mechanism underneath it fully
explicit, per review.

- **Server-side verification only.** The staff/admin password is submitted via a form to a
  Server Action and compared with `bcrypt.compare()` against `STAFF_PASSWORD_HASH` /
  `ADMIN_PASSWORD_HASH`. The plaintext password is never compared, logged, or stored
  client-side; the hash never leaves the server.
- **Session cookie.** A signed/sealed token (via `iron-session` or a `jose`-signed JWT)
  containing only `{ role: "staff" | "admin", issuedAt }` — no server-side session table,
  since there's no per-user state to store. Cookie flags: `HttpOnly` (inaccessible to any
  client-side JavaScript, mitigating XSS token theft), `Secure` (HTTPS-only), `SameSite=Lax`
  (sent on normal same-site navigation and form submissions, withheld on cross-site requests —
  the primary CSRF mitigation).
- **Expiration.** Sliding expiry — e.g., valid 12 hours from issuance, silently extended on
  activity within that window (checked in `middleware.ts`), up to a hard cap (e.g., 24h)
  requiring re-entry of the password. Exact durations live in `system_settings`/env, not
  hard-coded in route code.
- **Logout.** A Server Action clears the cookie (sets it with an immediate past expiry).
  Because sessions are stateless signed tokens, a token that leaked before logout remains
  cryptographically valid until its own natural expiry — an explicit, documented tradeoff of
  the no-accounts model, not a silent gap.
- **Staff vs. admin privilege state.** Encoded as the single `role` claim on the same cookie
  (`admin` implies `staff`), rather than two separate cookies — access checks reduce to one
  ordinal comparison.
- **Admin re-authentication/elevation.** Entering the admin PIN while a valid staff session
  exists elevates that same session's `role` claim to `admin` (re-issuing the signed cookie);
  it does not require re-entering the staff password. Recommended: admin elevation carries its
  own, shorter idle expiry (e.g., 30–60 minutes) that downgrades back to `role: "staff"`
  rather than logging out entirely — configurable, not hard-coded.
- **CSRF / same-origin.** `SameSite=Lax` already blocks the cookie on cross-site POSTs; Next.js
  Server Actions additionally validate the request's `Origin`/`Host` header against the
  deployment origin. These two layers are sufficient for this threat model — no hand-rolled
  CSRF token is introduced. Any Route Handler that mutates state outside the Server Action
  path gets an explicit same-origin check.
- **Repeated-login-attempt protection.** The `login_attempts` table throttles failed attempts
  per hashed IP and role within a rolling window (e.g., a short delay or temporary lockout
  after several failures in 15 minutes) — intentionally simple, matched to the actual threat
  model of a small school tool, not a dedicated rate-limiting service.
- **No password stored client-side.** The login form posts directly to a Server Action over
  HTTPS; nothing about the password is cached in `localStorage`/`sessionStorage`.
- **No secrets in the browser bundle.** `STAFF_PASSWORD_HASH`, `ADMIN_PASSWORD_HASH`, and
  `SESSION_SECRET` are server-only environment variables — never prefixed `NEXT_PUBLIC_`, so
  Next.js structurally excludes them from any client bundle.

This remains lightweight by design — no accounts, no per-user identity, no password-reset
flow — the specification above is about making the *mechanism* rigorous, not about turning
this into an account system.

## 16. Bulk-import architecture (~1,500 existing photos): a standalone worker, not a web request

**Corrected this review** — this is the most consequential fix in this revision. The first
draft did not explicitly rule out running bulk processing inside a Vercel Server Action/API
request, which would not actually work: serverless function execution has a hard time limit
(seconds to a few minutes depending on plan), far short of what processing hundreds of images
sequentially through AI calls requires. A single long-running request is not a viable
execution model at any Vercel plan tier.

**v1 design:** bulk import runs as a **standalone Node.js script**
(`scripts/import/run.ts`, invoked as `npm run import:bulk`), executed by an operator (you, or
me as engineer) from a local machine or any persistent runtime — explicitly **not** as part
of the deployed Next.js application's request/response cycle. This script:

- Imports the **same domain/provider modules** the web app uses (`lib/ingestion`, `lib/ai`,
  `lib/google/drive`, `lib/metadata-providers`, `lib/db`) — one implementation of the
  identification/enrichment/duplicate pipeline, not a second copy of the logic.
- Connects to the same Postgres database directly (a long-lived script suits a direct or
  session-mode connection better than the serverless app's transaction-pooled connection —
  both are valid Postgres connection profiles for their respective contexts; the exact choice
  is a Phase 10 implementation detail, not a Phase 0 lock-in).
- Loops over `ingestion_items`: claims the next pending batch (size from
  `ingestion_jobs.config.batch_size`), runs each through the shared pipeline, persists
  progress to Postgres after every single item (not just at batch end), and sleeps/backs off
  between batches to respect API rate limits.
- Is safely interruptible at any point — because progress is persisted per-item, killing the
  process (Ctrl+C, closing the laptop, a crash) never corrupts state. **Resuming is just
  re-running the script**: it skips `completed`/`skipped_duplicate` items, retries `failed`
  items under the configured retry cap, and continues any still-`pending` items.
- Never guesses on ambiguous input: multiple-books-in-one-photo detection routes to
  `needs_review` exactly as designed in the first draft.

**The admin web UI's role** is to create and observe job records — starting a job inserts an
`ingestion_jobs` row and enqueues `ingestion_items`; viewing progress reads the same counters
the script updates; "pause" sets a job status the running script checks between items and
exits on. The web app never executes the processing loop itself.

**How this runs during initial catalog creation:** the operator runs the script from a local
machine (or any always-available runtime), pointed at the target Supabase database, during
the supervised Phase 10/11/12 batches — a deliberately manual, supervised trigger for what is
explicitly framed as a one-time/occasional bulk operation, not something needing 24/7
infrastructure.

**How this could evolve later, if automated/unattended background processing is ever wanted**
(documented, not built now): either (a) a small persistent worker process on a low-cost
always-on host (e.g., Fly.io/Railway) that polls for queued jobs and runs them automatically
when an admin clicks "Start Import," or (b) a Vercel Cron job that invokes a Route Handler
every few minutes, each invocation processing one small batch within the function's time
limit and returning — a serverless-compatible way to achieve the same resumable behavior
without a separate host. Both are compatible with the existing `ingestion_jobs`/
`ingestion_items` schema with no data-model change; only the execution host changes.

## 17. Taxonomy architecture

Unchanged from the first draft: `physical_categories` is admin-managed (create/rename/
deactivate, never a hard delete that would orphan books); AI always selects among existing
active categories, never creates one; gap analysis is admin-triggered, not continuous, and
proposals (`taxonomy_suggestions`, now with `supporting_book_ids` as an array rather than a
join table — see `docs/DATA_MODEL.md` §12) require explicit admin approval before any
category is created or book reassigned.

## 18. Confidence architecture

Unchanged in behavior from the first draft; the underlying table is now
`book_field_provenance` with a four-way `source_type` (external / AI-inferred /
human-corrected / human-verified) and a full evidence history rather than only the latest
value — see `docs/DATA_MODEL.md` §6. Thresholds remain centralized in `system_settings`;
teachers never see a confidence number, only admins do.

## 19. Review-queue architecture

Unchanged: admin dashboard sections are filtered views over `books`, `review_flags`,
`book_duplicates`, and `taxonomy_suggestions` — no separate queue tables.

## 20. Reading list architecture

Unchanged: `reading_lists` + `reading_list_items`, no accounts, no ownership.

## 21. Privacy & security architecture

Unchanged from the first draft (no child PII anywhere in the schema; voice transcript never
persisted; search queries never logged by default; secrets exclusively in environment
variables; sessions are HTTP-only/Secure/SameSite cookies; uploads validated by type/size;
Drizzle produces only parameterized queries). The explicit session/auth mechanism is now
fully specified in §14 rather than summarized.

## 22. Deployment architecture

Unchanged from the first draft (Vercel for the app, Supabase Postgres with pooled
connections, separate dev/production environments) — with one addition: the bulk-import
script (§16) is **not deployed to Vercel** and does not share Vercel's execution-time
constraints; it runs wherever the operator runs it, connecting to the same database over a
connection profile suited to a long-lived process rather than serverless bursts.

## 25. Decisions locked now vs. kept configurable

**Locked** (revised this review):

- Next.js + React + TypeScript + Tailwind
- Postgres (via Supabase) as the canonical database
- **Drizzle** (schema, migrations, and queries) — revised from Kysely this review
- No individual teacher/admin accounts — two shared-secret role gates, fully specified in §14
- **Books and physical copies are separate entities** (`books` / `book_copies`) — new this
  review
- One required primary physical category per active book; unlimited many-to-many tags
- Google Drive = original-image source of truth; Google Sheets = generated projection, never
  canonical
- **Original capture and display cover are distinct, with a defined, configurable fallback
  order** — sharpened this review
- No AI-automatic category creation; no silent duplicate merges; no invented bibliographic
  data
- pgvector for embeddings, inside the same Postgres database
- **Bulk import runs as a standalone script/worker, never inside a Vercel request** — new
  this review
- **Search always degrades gracefully to pure-SQL layers when AI/embeddings are unavailable**
  — new this review
- Server Actions / Route Handlers pattern for the web app (no separate backend service)

**Configurable / explicitly deferred:**

- Concrete AI provider(s) for vision/LLM/embeddings
- Confidence thresholds, category-health thresholds, search ranking weights
  (`system_settings`)
- Google Drive auth strategy detail — pending real folder inspection in Phase 6
- Display-cover fallback priority order — a sensible default is set (§7), but overridable via
  `system_settings`
- Ingestion batch sizes and retry limits
- Embedding model/dimension
- Google Sheet sync cadence
- **Work-group linking** (`work_groups`) — deferred entirely until a real same-work/
  different-language case exists in the collection
- Application name, brand palette, and logo — pending assets
