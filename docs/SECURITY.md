# Security

Status: reflects what Phase 1 actually implements. High-level security architecture was
proposed in `docs/ARCHITECTURE.md` §14/§21 during Phase 0; this document tracks the real,
built mechanism and is the first doc in the target structure to graduate out of
`ARCHITECTURE.md`, per the plan to split docs out once their subject is operationally real.

## Authentication mechanism

- **Password storage:** the staff and admin secrets are never stored in the codebase or
  database. `STAFF_PASSWORD_HASH` / `ADMIN_PASSWORD_HASH` hold bcrypt hashes (cost factor 12,
  generated by `scripts/hash-password.mjs`) as environment variables only.
- **Verification:** `lib/auth/password.ts` wraps `bcrypt.compare()`, always server-side, in a
  Server Action (`lib/auth/actions.ts`). The plaintext password is submitted via a standard
  form POST over HTTPS in any real deployment and is never logged.
- **Session token:** a signed JWT (HS256, via `jose`), containing only `{ role, adminExpiresAt?,
  iat, exp }` — no password, hash, or identity. Signed with `SESSION_SECRET`. There is no
  server-side session store; the token is the entire session state.
- **Cookie attributes:** `HttpOnly` (inaccessible to any client-side JavaScript — mitigates
  XSS token theft), `Secure` in any real (HTTPS) deployment, `SameSite=Lax` (withheld on
  cross-site requests — the primary CSRF mitigation), `Path=/`.
- **Expiration:** a 12-hour session, silently renewed (`maybeRenewSessionToken`) once less
  than half its lifetime remains, checked on every request in `src/proxy.ts` (Next.js 16's
  renamed middleware convention). Admin elevation carries its own 45-minute window
  (`adminExpiresAt`), independent of and shorter than the overall session — once it lapses,
  the next renewal silently re-issues a plain staff-level session rather than logging the
  user out entirely.
- **Logout:** clears the cookie. Because the session is a stateless signed token, a copy that
  leaked before logout remains cryptographically valid until its own natural expiry — an
  explicit, accepted tradeoff of the no-accounts model (documented in `docs/DECISIONS.md`),
  not an oversight.
- **CSRF:** `SameSite=Lax` plus Next.js Server Actions' built-in `Origin`/`Host` validation.
  No hand-rolled CSRF token was introduced — unnecessary complexity for this threat model.
- **Brute-force protection:** `lib/auth/rateLimit.ts` throttles repeated failed attempts per
  hashed-IP-and-role within a rolling window (8 attempts / 15 minutes). **This is an in-memory,
  Phase 1 interim implementation** — the real design (`docs/DATA_MODEL.md`'s `login_attempts`
  table) lands in Phase 4. In-memory state resets on server restart and doesn't share state
  across multiple server instances; acceptable for local development and this phase's scope,
  not for a real multi-instance production deployment.
- **No secrets in the client bundle:** `STAFF_PASSWORD_HASH`, `ADMIN_PASSWORD_HASH`,
  `SESSION_SECRET` are never prefixed `NEXT_PUBLIC_`, so Next.js structurally excludes them
  from anything shipped to the browser.

## A real bug this phase caught: `Secure` cookies and WebKit

While testing on the mobile/WebKit Playwright project (standing in for iPhone Safari, per the
brief's explicit requirement to test on that engine), the session cookie was silently dropped
on the second navigation after login — the first request worked, every subsequent
client-side navigation didn't. Root cause: the cookie's `Secure` flag was tied to
`NODE_ENV === "production"`, and `next start` sets `NODE_ENV=production` even when serving
plain HTTP locally. Chromium is lenient about `Secure` cookies on `localhost`/`127.0.0.1` as a
developer convenience; WebKit does not reliably extend that same leniency to `fetch()`-driven
client-side navigations (as opposed to full top-level page loads), so the cookie was accepted
once and then silently excluded from subsequent same-origin requests.

Fix: `sessionCookieOptions()` now supports an explicit `SESSION_COOKIE_SECURE` override,
defaulting to the previous `NODE_ENV`-based behavior (correct for any real HTTPS deployment)
but overridable for a deliberate plain-HTTP context (this test suite sets it to `false`). This
is exactly why the brief requires testing on real device engines, not just Chromium — this
class of bug would have silently broken the app for actual iPhone Safari users on any
non-HTTPS environment (e.g., an early staging deployment before a custom domain was
configured).

## A real bug found live: bcrypt hashes and `.env.local` (or ANY `.env` file's mere presence)

Setting up real local credentials for the first time (2026-09-14), a correct staff password
kept failing with "That password didn't work" even though the stored hash verified correctly
against the password in isolation (confirmed directly with `bcrypt.compareSync`). Root-caused
by adding temporary logging to the Server Action and comparing the hash it actually received
against what was written to `.env.local`: **the hash was missing its `$2b$12$...` prefix.**

The cause: a bcrypt hash always contains literal `$` characters (`$2b$12$<salt><hash>`).
Next.js's environment-variable loader runs a `dotenv-expand`-style pass that treats `$word`
as a reference to another environment variable to substitute in — `$2b`, `$12`, and the
leading word-characters of the salt each looked like an (undefined) variable name and were
silently replaced with nothing. This is not limited to values that come from a `.env` file:
**verified directly against a real server that as soon as *any* `.env.local` file exists
anywhere in the project — even with unrelated content — Next.js's expansion pass runs against
the *entire* process environment, including values injected directly by a parent process
(e.g. Playwright's `webServer.env`, or a CI job's env block).** With no `.env.local` present
at all, the same unescaped hash passed via the shell worked correctly; the moment a
`.env.local` file existed, it broke — confirmed by toggling the file's presence and re-testing
each way, not inferred from documentation alone.

**Fix, in two places both needed:**
- `scripts/hash-password.mjs` now prints the hash pre-escaped (`$` → `\$`), so pasting its
  output directly into `.env.local` survives intact. The escaped form is what the script
  documents as correct — don't "clean up" the backslashes.
- `playwright.config.ts`'s `webServer.env` escapes its own generated hashes the same way,
  since the E2E suite is just as exposed to this once a developer's own `.env.local` happens
  to exist in the working directory during a local test run.

Anyone manually typing or pasting a bcrypt hash into any `.env*` file — for this project or
any other Next.js project — should escape every `$` as `\$` first. This is worth knowing
generally, not just for this codebase.

## What's explicitly out of scope for Phase 1

- No database, so no `login_attempts` table yet (see above).
- No file uploads yet, so upload validation (type/size allowlisting) isn't implemented —
  lands with the Add-a-Book flow in Phase 7.
- No Google/AI credentials exist yet, so there's nothing to scope least-privilege for yet.

## Verified, not assumed

Contrast ratios, cookie behavior, and route protection in this phase were checked with real
tooling (a small contrast-ratio script, Playwright against real Chromium and WebKit engines,
and reading actual server logs during debugging) rather than asserted — see
`docs/ACCESSIBILITY.md` for the contrast findings.
